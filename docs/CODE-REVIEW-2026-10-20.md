Python 테스트는 메모리 SQLite와 모의 Kakao 응답을 사용하는 기존 fixture를 확인한 후 실행했다. 테스트 요청 메타데이터는 기존 로깅 동작에 따라 `logs/http.jsonl`에 추가될 수 있다. Starlette의 `httpx` TestClient 사용 중단 예정 경고가 출력되었으나 테스트 실패는 없었다.

이번 검토에서는 실제 브라우저 E2E, 실제 Kakao 계정 로그인, 운영 Nginx 적용 및 외부 DB 검증을 수행하지 않았다. 기존 테스트 통과가 아래 미검증 시나리오까지 보장하지는 않는다.

### BE-01 — P1: 인증 없이 게시글 등록 가능

- 위치: [api/routers/board.py:9](../api/routers/board.py#L9), [api/routers/board.py:36](../api/routers/board.py#L36), [app/models/board.py:5](../app/models/board.py#L5)
- 발생 조건: 쿠키 없이 `/board/insertBoard` 또는 `/api/board/insertBoard`에 `title`, `boardCd`를 전달한다.
- 영향: 사용자 확인 없이 DB에 게시글을 생성할 수 있다. 모델에 작성자 정보도 없어 작성자 단위 권한 확인이 어렵다.
- 수정 제안: 회원 전용 쓰기라면 `Depends(current_account)`와 출처 검사를 적용하고 작성자를 저장한다. 익명 쓰기가 의도된 서비스라면 해당 정책을 명시하고 별도 남용 방지를 설계한다. P1은 회원 전용 쓰기를 전제로 한 우선순위다.
- 검증: 메인 에이전트가 기존 fixture와 게시글 `SessionLocal`의 임시 DB 대체를 사용하여, 쿠키 없는 등록 요청의 **200 응답**을 확인했다. 실 DB와 외부 서버는 사용하지 않았다.

### BE-02 — P2: 동일한 로그인 ID를 DB가 중복 허용

- 위치: [api/routers/users.py:24](../api/routers/users.py#L24), [app/models/user.py:12](../app/models/user.py#L12)
- 발생 조건: 같은 ID의 가입 요청이 각각 중복 조회를 통과한 뒤 저장한다. 현재 중복 검사는 조회 후 삽입으로 분리되어 있다.
- 영향: 모델에 UNIQUE 제약이 없어 같은 ID의 계정이 저장될 수 있다. 로그인은 한 행을 선택하므로 계정 식별이 모호해진다.
- 수정 제안: ID에 DB UNIQUE 제약을 추가하고, 충돌 시 rollback 후 409를 반환한다. 기존 DB에는 중복 확인·정리와 별도 스키마 변경이 필요하며 `create_all()`만으로 기존 테이블 제약이 갱신되지는 않는다.
- 검증: 메인 에이전트가 모델로 생성한 메모리 SQLite에 같은 ID의 User 두 개를 삽입하여 **2행 저장**을 확인했다. 실제 동시 HTTP 요청과 실제 DB의 추가 제약 존재 여부는 검증하지 않았다. 기존 테스트는 순차 중복만 검사한다.

### BE-03 — P2: 게시글 등록의 DB 세션 정리 누락

- 위치: [api/routers/board.py:38](../api/routers/board.py#L38), [api/routers/board.py:45](../api/routers/board.py#L45), [app/db/database.py:13](../app/db/database.py#L13)
- 발생 조건: 등록에서 직접 만든 `SessionLocal()`을 사용하여 commit·refresh 후 반환하거나 DB 작업 중 예외가 발생한다.
- 영향: 명시적인 close·finally 경로가 없다. refresh로 시작된 트랜잭션과 연결이 객체 정리 전까지 유지될 수 있어 반복 요청에서 자원 부족 위험이 있다.
- 수정 제안: 다른 라우트처럼 `Depends(get_db)`로 수명을 관리하고, 트랜잭션 예외 시 rollback과 통제된 응답을 처리한다.
- 검증: 세션 생성·반환 및 공통 의존성의 finally-close 경로를 대조했다. 연결 풀 고갈·부하 재현은 수행하지 않았다.

### FE-01 — P3: 공백 아이디·이름이 빈 값으로 가입됨

- 위치: [web/app.js:154](../web/app.js#L154), [web/app.js:156](../web/app.js#L156), [web/index.html:38](../web/index.html#L38), [app/schemas/user.py:5](../app/schemas/user.py#L5)
- 발생 조건: 가입 폼의 아이디·이름에 공백만 입력. HTML `required`는 이를 통과시키지만 JS의 `trim()` 이후에는 빈 문자열이 된다.

- 수정 제안: 프론트에서 공백 제거 후 필수값을 검사하고, 서버에서도 아이디·이름의 공백 정규화와 최소·최대 길이, 이메일 형식을 검증한다. 서버 `email`도 단순 str이므로 브라우저의 이메일 형식 검사만으로는 API 직접 요청을 통제하지 못한다. 비밀번호는 BE-04의 별도 정책을 적용하며 임의로 trim하지 않는다.
- 검증: 서브에이전트의 정적 검토 후 메인 에이전트가 기존 메모리 SQLite fixture로 재현. `POST /api/user/signUp`에 빈 `userId`·`userNm`을 보내 **201**, 빈 값이 담긴 프로필 응답을 확인했다. 실제 DB는 사용하지 않았다.

## 정상 동작 근거와 검토 한계

- 프론트엔드 요청·응답 필드와 API 인터페이스가 일치하며, 로그아웃 204 처리, 요청 중 중복 제출 방지, 숨겨진 가입 필드 비활성화를 확인했다.
- 프로필과 메시지는 `textContent`로 출력한다. 진단 로그에 비밀번호·응답 본문을 넣지 않는 코드 경로를 확인했다.
- OAuth state의 서명·만료·쿠키 대조, 공급자별 계정 고유 제약, 이메일만으로 로컬 계정과 자동 연결하지 않는 처리를 확인했다.
- 기존 56개 테스트는 인증·OAuth·CORS·로그·정적 제공 계약을 검증하지만 실제 JavaScript 실행과 다중 탭, 게시글 권한, 동시 가입, 부하를 검증하지 않는다.
- Spring 예제 소스에서 추가 결함은 확정하지 못했으나, Wrapper 오류로 빌드·테스트 성공 여부는 확인할 수 없다.
- 소스 검토 결과이며 운영 환경 전체의 보안 검증 결과는 아니다. 비밀값·실제 데이터·기존 로그·실제 DB 제약을 확인하지 않았다.

## 권장 수정 순서와 완료 기준

1. **게시글 쓰기 권한 확정 및 BE-01 대응:** 회원 전용이면 쿠키 없는 등록은 401, 정상 회원 등록은 성공하는 테스트를 추가한다.
2. **가입 데이터 정합성 보완:** BE-02의 UNIQUE 제약 및 충돌 처리, BE-04·FE-01의 입력 검증을 함께 적용한다. 빈 비밀번호·빈 ID는 422, 동시 중복 가입은 성공 1건과 409 응답으로 검증한다.
3. **DB 자원·조회량 관리:** BE-03·BE-05를 수정하고 성공·실패 모두 세션이 닫히는지, 최대 페이지 크기를 넘지 않는지 확인한다.
4. **화면 세션 동기화:** FE-02를 수정하고 두 탭에서 로그아웃·계정 전환·세션 만료 시 개인정보가 갱신·삭제되는지 브라우저로 확인한다.
5. **사용할 배포 경로 및 Spring 도구 정비:** INT-01은 해당 예제 사용 시 수정하고, TOOL-01을 해결한 후 Java 테스트 결과를 별도로 확보한다.

위 수정은 이번 작업에서 적용하지 않았다. 이 문서는 두 서브에이전트의 결과를 중복 제거하고 메인 에이전트가 근거를 확인하여 작성한 수정 제안 보고서다.
